# 边界问题清单：任何功能都要防"无限膨胀"

> 复盘 2026-09-28 Ops/Trace 页面"越用越卡"问题后沉淀的规范。**以后在本项目加任何功能，先把第三节的清单逐项过一遍。**

## 一、本次真实案例（教训来源)

**现象**：Ops / Trace 两个页面，用得越久越卡，最后卡到不想用。

**数据源头**:`.blh/traces/{date}.jsonl` 和 `.blh/usage.jsonl`，每跑一个 turn 追加一行，**只增不减**。2026-09-28 当天 258 行；按这个速度，重度使用一周就是几千行。

**旧实现的三个"全量"**（每次请求/每次轮询都做）:

1. **全量读**：服务端 `readFileSync` 把整个文件读进内存；
2. **全量算**：每行 `JSON.parse` 一遍、fold 成 turns 一遍、usage 从头累加一遍;
3. **全量画**：前端每秒轮询拿到全量数据，整页 `setState` 重画。

**后果**：文件像只进不出的水桶，每次喝一口水都要把整桶倒出来再舀。文件越大 → 每次请求越慢 → 页面越卡，恶性循环。

**修复**（对应实现见第四节）:

- 读：书签式增量读——记住上次读到第几个字节，只读新增部分；
- 算：结果缓存 + 脏标记——没有新数据不重算，usage 用累加器只加新增记录；
- 画：首次只取尾部 200 行（显示"显示 200 / 共 258 行"），之后每 2 秒只拉增量；数据没变不 `setState`。

**效果**：读取成本从"和文件总量挂钩"变成"只和新增量挂钩"。文件涨到 10 万行，每次请求也只读新写入的几行。

## 二、核心原则

**加任何功能前，先问一句：这个功能读/算/展示的数据，会不会只增不减、越用越大？**

只要答案可能是"会"，设计里就必须给出增量机制或明确上限，**禁止写"全量读 / 全量算 / 全量画"**。

## 三、Checklist（加功能时逐项过）

### 1. 识别：数据会不会无限长大？

- 日志、trace、用量记录、会话历史、消息列表、任务列表……凡是**追加型**数据，默认会无限长大。
- 会长大 → 下面 2/3/4/5 必须全部落实；不会长大（如配置文件）→ 不用。

### 2. 读取：有没有"书签"？

- 禁止：每次从头读全量文件/全表。
- 应该：记录 offset / cursor / lastId，只读增量。
- 必须处理的边界：半行（写了一半的行下次拼上）、坏行（占位不丢行号）、文件被截断或删除重建（检测 size 变小，重置重来）。参考 `src/tracing/store.ts` 的 `JsonlTail`。

### 3. 计算：有没有缓存 + 脏标记？

- 禁止：每次请求把全部数据重新 parse / fold / 聚合。
- 应该：结果缓存，有新数据才重算；统计类用增量累加器（参考 `src/tracing/pricing.ts` 的 `createUsageAccumulator`），防止追加数据后重复累加翻倍。
- 注意缓存自己的边界：按 key 缓存的（如按日期）要有淘汰上限（本项目 LRU 保留 8 天），否则缓存本身又成了新的无界点。

### 4. 展示：有没有分页/截尾 + 防重画？

- 禁止：把全部数据塞给前端、每次轮询整页重画。
- 应该：首次只给尾部 N 条 + 总数（"显示 X / 共 Y 行"），之后增量轮询追加；数据没变不 `setState`（参考 `TracePage.tsx` 的 JSON 比较）。

### 5. 测试：有没有"数据变多"的用例？

- 单测至少一条：追加数据后，成本不随总量翻倍。例如断言"追加 1 行只多读 1 行的字节"（`stats().bytesRead`）、"usage 追加后不翻倍"。
- 参考 `test/tracing/store.test.ts` 的 14 条用例：半行、坏行、截断、删除重建、LRU 淘汰、usage 防翻倍。

## 五、项目内已确认的"只增不减"数据点

以下数据点已确认是追加型、只增不减。新功能只要读写它们，必须按第三节执行：

- `<workdir>/.blh/traces/{date}.jsonl` —— trace 事件（本次已修）
- `<workdir>/.blh/usage.jsonl` —— 用量记录（本次已修，走 `usageTail` 增量）

以后新增的追加型存储（日志、历史、记录类），落地前先补到这张表里，并按清单设计。
