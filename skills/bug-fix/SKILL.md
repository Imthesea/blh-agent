# bug-fix

对 bug 做“复现 → 定位 → 修复 → 验证 → 记录”的闭环处理。核心目标不是“让报错消失”，而是**找到根因、最小修复、并证明修好了**。

## 触发时机

当用户描述一个故障、报错、异常行为，或要求“修一下 / 排查 / 看看到底为什么”时使用本 skill。

## 核心原则

1. **先复现，再动手**：复现不了就明说，不靠猜改代码。
2. **一次只改一个根因**：避免把多个无关改动混在一起。
3. **改完必须验证**：没有验证的修复不算完成。
4. **最小改动**：不顺手重构无关代码。

## 步骤

### 1. 复现
- 收集信息：触发命令、报错堆栈、相关日志（`<workdir>/.blh/logs/`）、环境版本。
- 收敛到**最小复现步骤**：用最简单输入稳定触发同一报错。
- 若无法复现：明确说明，并列出还缺哪些信息（输入样例、完整日志、环境）。

### 2. 定位
- 用 `read_file` / `glob` 读相关代码，先形成**一个最可能的假设**，再验证，不撒网式乱翻。
- 用日志、trace、二分法逐步缩小范围；每个结论都要有可指认的证据（文件 + 行号）。

### 3. 修复
- 只改引发问题的根因，做最小 diff。
- 在改动处说清“为什么这样改、依据是什么”。
- 禁止用 `try-catch` 吞掉异常或 `as any` 掩盖类型问题来“糊过去”。

### 4. 验证
- 重跑最小复现步骤，确认报错消失。
- 跑相关测试：`pnpm test`（vitest）或针对该模块的用例；有回归风险时后台跑长测试。
- `git diff` 自查改动，确认没有夹带无关变更。

### 5. 记录
- commit message 写清：根因 + 修复方式 + 验证结果。
- 若是会反复出现的同类问题，沉淀到 `memory`，下次直接复用排查路径。

## 输出格式

```
## 根因
一句话说明问题出在哪、为什么。

## 修复
列出改动文件与关键 diff，说明为什么这么改。

## 验证
复现步骤结果 + 测试结果 + git diff 自查结论。
```

## 禁止事项
- 不绕过权限体系执行破坏性命令（rm -rf、force push 等仍会被硬拦截）。
- 不“改到能跑就行”，必须能解释根因。
- 不在一次修复里混入多个无关改动。
