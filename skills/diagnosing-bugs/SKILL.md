# 缺陷诊断

一套针对疑难 bug 的纪律性流程。只有当你明确说明理由时，才允许跳过某个阶段。

探索代码库时，先读 `GLOSSARY.md`（如果存在）建立对相关模块的清晰心智模型，并查看你正在改动的区域里的 ADR。

## 脱敏（Redact）

本 skill 会让你展示命令、输出和采集到的产物。**先脱敏所有机密**：把敏感值替换成 `<REDACTED>`。把回路构建成依赖环境变量，让凭据留在环境里、而不是出现在你展示的内容中。采集到的产物里带 auth 头：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断 bug，明确说明并向用户求助。

## 阶段 1：建立反馈回路

**这才是本 skill 的核心。** 其余都是机械操作。只要你有一个针对这个 bug 的**紧致**的通过/失败信号（一个会在这个 bug 上变红的信号），你就能找到根因；二分法、假设检验、插桩都只是在消费这个信号。如果没有它，盯着代码看再久也没用。

在这里投入不成比例的努力。**要激进、要有创造力、绝不放弃。**

### 构建回路的方法，大致按优先级排列

1. **失败测试**：在任何一个能触达 bug 的接缝处写——单元、集成、e2e。
2. **Curl / HTTP 脚本**：打向正在运行的开发服务器。
3. **CLI 调用**：用固定输入（fixture）跑，把 stdout 与已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，并对 DOM/console/network 做断言。
5. **回放采集到的 trace**：把真实的网络请求/载荷/事件日志存盘，隔离地重放它走一遍代码路径。
6. **一次性 harness**：拉起系统的最小子集（一个服务、mock 掉依赖），用单次函数调用命中 bug 代码路径。
7. **属性 / 模糊测试回路**：如果 bug 是“有时输出错误”，跑 1000 个随机输入找失败模式。
8. **二分 harness**：如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化“在状态 X 启动、检查、重复”，从而能 `git bisect run`。
9. **差分回路**：把同一个输入分别跑旧版本 vs 新版本（或两种配置），diff 输出。
10. **HITL bash 脚本**：最后手段。如果必须由人来点击，用 `scripts/hitl-loop.template.sh` 驱动**那个人**，让回路仍然是结构化的。采集到的输出回馈给你。

把正确的反馈回路建起来，bug 就修好 90% 了。

### 收紧回路

把回路当成产品来打磨。一旦有了**一个**回路，就**收紧**它：

- 能更快吗？（缓存初始化、跳过无关的 setup、缩小测试范围。）
- 能让信号更锐利吗？（断言在**具体症状**上，而不是“没崩溃”。）
- 能更确定吗？（固定时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒还 flaky 的回路比没有回路强不了多少；一个 2 秒的确定性回路才是紧致的，是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压、缩小时间窗口、注入 sleep。50% 抖动率的 bug 是可调试的；1% 不行，所以不断把复现率往上抬，直到可调试为止。

### 当你确实建不出回路时

停下并明确说出来。列出你试过的方法。向用户要：(a) 能复现该问题的环境访问权，(b) 一份脱敏的采集产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 允许添加临时生产插桩的许可。**不要**在没有回路的情况下直接进入假设。

### 阶段 1 完成标准：一个紧致、能变红的回路

当回路是**紧致的**且**能变红**时，阶段 1 才算完成：你能说出**一条命令**（脚本路径、测试调用、curl），这条命令你**已经至少跑过一次**（展示调用和输出，脱敏），并且：

- [ ] **能变红**：它驱动真实的 bug 代码路径，并断言**用户的确切症状**，因此能在当前 bug 上变红、修复后变绿。不是“没报错地跑完”；它必须能**抓住这个具体的 bug**。
- [ ] **确定性**：每次运行结论一致（flaky bug：按上文固定出一个高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可运行**：能无人值守地跑；只有在通过 `scripts/hitl-loop.template.sh` 时才需要人在回路里。

如果你发现自己在这条命令存在之前就开始读代码构建理论，**停下：直接跳到假设正是本 skill 要防止的失败模式。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路，看它在 bug 出现时变红。

确认：

- [ ] 回路产生的是**用户**描述的失败模式，而不是一个碰巧在旁边的不同失败。修错 bug = 修错地方。
- [ ] 失败可跨多次运行复现（对非确定性 bug：复现率足够高、能支撑调试）。
- [ ] 你已捕获确切症状（错误消息、错误输出、变慢的耗时），以便后续阶段能验证修复真的针对它。

### 最小化

一旦变红，就把复现缩到**仍然会变红的最小场景**。一次只砍一样——输入、调用方、配置、数据、步骤——每砍一样都重跑回路，只保留对失败“有承重”的东西。

为什么要费这个劲：最小复现能缩小阶段 3 的假设空间（要怀疑的活动件更少），并成为阶段 5 的干净回归测试。

完成标志：**剩下的每个元素都有承重**——去掉任何一个，回路都会变绿。

在**复现并最小化**之前，不要继续。

## 阶段 3：提出假设

在测试任何一个假设之前，先产出 **3–5 个排序过的假设**。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：陈述它给出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。”

如果你无法陈述预测，这个假设就是“感觉”：丢弃或锐化它。

**在测试前把排序后的清单给用户看。** 他们往往有能瞬间重排的领域知识（“我们刚对第 3 条部署了改动”），或知道已经排除过哪些假设。便宜的检查点，省大把时间。不要卡在这上面；如果用户不在，按你的排序继续。

## 阶段 4：插桩

每个探针必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十行日志。
2. **定向日志**，打在能区分假设的边界上。
3. 绝不“把一切都打日志然后 grep”。

**给每一条调试日志打唯一前缀标签**，例如 `[DEBUG-a4f2]`。收尾时清理就变成一次 grep。没打标签的日志会留下来；打了标签的会死掉。

**性能分支。** 对性能回归，日志通常用不上。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），再二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

**在修复之前**写回归测试，但只有当存在**正确的接缝**时才写。

正确的接缝，是测试能在调用点真实地复现**真实 bug 模式**的地方。如果唯一可用的接缝太浅（bug 需要多个调用方时只能写单调用方测试；单元测试无法复刻触发 bug 的调用链），在那里写回归测试只会给你虚假的信心。

**如果不存在正确的接缝，那本身就是发现。** 记录下来。代码库的架构正在阻止这个 bug 被锁死。把这一点标记出来留给下一阶段。

如果存在正确的接缝：

1. 把最小化后的复现，在那个接缝处变成一条失败测试。
2. 看它失败。如果你是通过改动代码或 fixture 强制造出的红，先在信任它之前 `diff` 一份干净副本来证明改动确实落了。
3. 应用修复。
4. 看它通过。
5. 用原始的（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6：收尾

宣告完成前必须：

- [ ] 原始复现不再出现（重跑阶段 1 回路）
- [ ] 回归测试通过（或“没有接缝”已记录在案）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试目录）
- [ ] 最终被证实正确的假设写进了 commit / PR 信息，让下一个调试者能学到
